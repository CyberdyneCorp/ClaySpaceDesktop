# An agent drives the application, and sees what it did

## Why

Every way into this application ends at a pointer on a window. That is the
right door for a sculptor and the only door there is, and it closes two things
we want.

The first is a sculptor's agent. A person should be able to say "block this in
as a subtool, mask the jaw, and smooth the seam" to an agent that then works
the application the way they would — and an agent that cannot *see* the
viewport is an agent guessing at whether a dab landed where it meant. Text
state is not enough for a program whose whole output is a surface.

The second is our own development agent, and it is the one that costs us daily.
This repository already measures itself well: 2,009 headless tests, 618 visual
captures regenerated by `cargo test`, a benchmark harness with a per-platform
baseline and a drift history. Every one of those runs against a *constructed*
document in a *fresh* process. None of them can be pointed at the session
sitting open in front of us — the one with the surface that is actually wrong,
the stall that only appears after forty strokes, the panel that only misdraws
once a hierarchy carries four levels. "Reproduce it in a test" is the right
instinct and it is also the reason a defect takes a day: the reproduction is
the work. An agent that can drive the live session and read a frame back is an
agent that can bisect a symptom in the state where the symptom exists.

The mechanism for both is already built and this change does not invent it.
`Command` is one enumeration through which *every* mutation already passes,
"commands are values, not closures", every ViewModel is exercisable with no
window and no GPU, and `OffscreenTarget` already renders a frame to RGBA8 rows
because a renderer that can only draw into a window can only be checked by
someone sitting in front of one. What is missing is a door onto that path for a
process that is not the View.

## What Changes

- **The application listens, from the moment it opens.** A Model Context
  Protocol server runs inside the running application for its whole life, on
  loopback, so an agent connects to the session a sculptor is already in
  rather than starting one of its own.
- **A new crate, `clayspace-mcp`**, holding the protocol, the tool surface and
  the listener. It depends on `clayspace-vm` and `clayspace-model` and on
  nothing below or beside them — no engine, no `egui`, no `wgpu`, no `winit` —
  so the whole tool surface is testable with neither a window nor the C++
  engine built.
- **The transport is MCP Streamable HTTP bound to `127.0.0.1`**, so any MCP
  client reaches it with a URL and no shim binary. The listening port and a
  bearer token are written to the session directory at `0600`, which is how a
  client on this machine finds the session and how one that cannot read that
  file is refused.
- **The tool surface is grouped by feature, roughly one tool per domain the
  application already has a ViewModel for**: sculpting, subtools and layers,
  placed objects and the manipulator, masking, curves, lattice, armature,
  representations and conversion, the document, history, the camera and view,
  references, booleans, jobs, session and diagnostics. Each takes an action and
  its arguments and dispatches to the same `Command` a menu item emits. Not one
  tool per `Command` variant: there are a hundred and thirty of them, and a tool
  list that long is a tool list an agent chooses badly from.
- **A tool for the vocabulary itself.** The server can be asked what actions a
  group offers and what each takes, so the agent learns the application's verbs
  at runtime instead of carrying a copy of them that goes stale.
- **The agent sees the viewport.** A capture tool returns the current frame as
  a PNG image content block, and every tool that changes something can return
  the frame *after* the change in the same result, so "did that land where I
  meant" costs one round trip rather than two.
- **A command from an agent is the same command as a click.** It enters the
  same queue, is applied on the interface thread between frames, is one entry
  in the same history, and is undone by the same undo. There is no second
  mutation path, and the guarantee that every mutation is observable in one
  place survives this change rather than being weakened by it.
- **The agent can wait for the application to be quiet.** Meshing, baking,
  import, export and save outlast a frame by design; a tool that returns before
  they finish returns a screenshot of a surface mid-flight. An idle barrier
  and job status are part of the surface.
- **The agent can measure.** Frame timing, the stall log, the memory ledger,
  the active backend and the fallbacks are readable, and an operation can be
  run under measurement so a latency figure comes from the live session rather
  than from a fresh process on a quiet machine.
- **What can destroy work is gated.** Reading, observing, sculpting and undoing
  run freely. Saving over a file, exporting, opening a document, discarding an
  unsaved document and quitting require a consent that is not the token: either
  an opt-in recorded in the session store or an answer from the person at the
  window. A refusal names the gate rather than failing silently.
- **The window says it is listening**, and says when an agent last acted, so a
  surface that moved on its own is attributable.
- **`serde` and `serde_json` enter the workspace**, confined to the new crate
  and to the tool boundary. No async runtime, no HTTP framework, and no base64
  crate: the listener is a thread per connection speaking HTTP/1.1 and
  JSON-RPC, which is the whole of what this transport is.

## Capabilities

### New Capabilities

- `agent-control`: an always-listening MCP server inside the running
  application — its lifetime, its loopback transport and authentication, the
  feature-grouped tool surface, the rule that every tool dispatches the same
  command path the interface does, the gating of what can destroy work, and
  what a refusal says.
- `agent-observation`: what an agent can see and measure of a live session —
  the viewport as an image, the correspondence between a capture and the state
  it is claimed to show, readback of scene and tool state, the idle barrier,
  and timing and memory figures taken from the running session.

### Modified Capabilities

- `mvvm-architecture`: the command path now has a second source that is not a
  View. "All mutations flow through a single command path" is what makes that
  safe and is restated as a rule about *every* source rather than about the
  View alone; the dependency-direction and forbidden-edge requirements extend
  to `clayspace-mcp`.
- `app-shell`: the status area reports whether the application is listening and
  when an agent last acted; the menu carries the server's controls; a command
  arriving mid-gesture has a stated outcome rather than an undefined one.
- `diagnostics`: the report carries whether the server is listening, on what
  port, and how much of this session's history came from an agent — the same
  reason the report already carries the engine revision and the container
  minor, which is that a bug report reconstructed by hand is a bug report
  filed against a guess.

## Impact

**New code.** `crates/clayspace-mcp` (protocol, transport, tool surface,
gating). Wiring in `clayspace-app`: an intake queue, a `winit` `EventLoopProxy`
so an arriving request wakes a `ControlFlow::Wait` event loop, application of
agent commands between frames, and capture-on-demand through the existing
`clayspace-view::offscreen` path.

**Dependencies.** `serde` and `serde_json` in `clayspace-mcp` alone, and `png`
for the encoder the workspace already carries. `deny.toml` and the generated
`ATTRIBUTION.md` both move. No `tokio`, no `hyper`, no `axum`, no `rmcp`, and
no base64 crate — the encoder for an image content block is thirty lines
against published vectors, which is less than a dependency to audit, license
and keep.

**Checks.** `tools/check_layering.py` gains the new crate and its forbidden
edges. The crate declares `#![forbid(unsafe_code)]` like every crate that is
not a bridge.

**Surface at risk.** A process on this machine that can read the session
directory can drive the application. That is the intended blast radius and it
is why the token file is `0600`, why the listener binds loopback only, why the
`Origin` header is checked, and why the destructive verbs are gated behind
something the token alone cannot supply.

**Documentation.** `docs/architecture.md` gains the layer and the reason it
sits where it does; `docs/features.md` and the README gain the door and how to
point a client at it.
