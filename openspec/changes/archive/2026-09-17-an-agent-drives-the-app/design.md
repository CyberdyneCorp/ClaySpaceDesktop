# Design

## Context

See `proposal.md` — Why. The requirements are in `specs/agent-control`,
`specs/agent-observation`, and the deltas to `specs/mvvm-architecture`,
`specs/app-shell` and `specs/diagnostics`.

Four properties of what is already here decide most of this design.

**There is one mutation path and it is a value.** `Command` is an enumeration
of a hundred and thirty variants covering every change; `CommandQueue` collects
them; the composition root applies them. It already carries
`Command::touches_document()` and `Command::label()`, which are most of what a
gate and a description need. Nothing in this change needs a second way in — it
needs a second *emitter*.

**The interface thread owns everything.** `Observable<T>` holds a
`Cell<u64>`, so every ViewModel is `!Sync`; the engine's safe wrapper is
`Send + !Sync` by design, so a document is not shared either; and `wgpu`'s
device and the window belong to the thread that made them. A server thread
therefore cannot hold a reference to any of it. Every read, every command and
every capture has to happen *on* the interface thread, between frames.

**The event loop sleeps.** `ControlFlow::Wait`, deliberately: an idle
application that redraws forever is the failure `Observable` exists to prevent.
A request arriving over a socket has to wake it, or an agent's command would sit
in a queue until someone moved the mouse.

**Rendering to an image already works.** `OffscreenTarget` renders through the
same `Renderer` and `Camera` as the window and reads back RGBA8 rows; 618 PNGs
are regenerated by `cargo test` through it. The screenshot tool is a caller of
something proven, not a new path.

The workspace also has no `serde`, no async runtime, and no HTTP anything. That
is a constraint, and the settled answer is in Decisions below.

## Goals / Non-Goals

**Goals**

- A door onto the *running* session, reachable by any MCP client with a URL.
- One tool surface that cannot drift from the application's command vocabulary,
  because the compiler will not let it.
- A capture that is the same renderer's output as the window's, at a size the
  caller chooses, correlated with the state it claims to show.
- A blast radius that is stated, small, and gated where it can destroy work.
- Everything above `clayspace-app` testable with no window, no GPU and no C++
  engine build.

**Non-Goals**

- Multi-user or cross-machine access. The door is loopback and stays loopback.
- An agent that *replaces* the interface. Where the interface refuses, the tool
  refuses; the server has no privileged verbs of its own.
- Writing benchmark baselines from a live session. Measurement here is
  evidence; `benchmarks/` stays the authority on what a run is judged against.
- MCP prompts and resources in the first cut. Tools are the whole surface;
  resources are a natural second step for the scene tree and the document, and
  nothing here forecloses them.
- Recording or replaying an agent session as a script. Worth having, not this.

## Decisions

### The server is a crate beside the View, not under it

`crates/clayspace-mcp` depends on `clayspace-model` and `clayspace-vm` and on
nothing else of ours. Not on `clayspace-view` (no `egui`, `wgpu` or `winit`),
not on `clayspace-engine`, not on `claycore`. It declares
`#![forbid(unsafe_code)]` and `tools/check_layering.py` gains its forbidden
edges.

The reason is the reason the View has the same rule: a tool surface that can
only be exercised with a window and a compiled C++ engine is a tool surface
nobody will test. With this arrangement, all hundred and thirty mappings, the whole
protocol and every gate are covered by tests that run in the ViewModel suite's
feedback loop.

*Alternative considered:* putting the server in `clayspace-app`, which is the
only crate that can already touch everything. Rejected — the composition root
is 4,700 lines and adding a protocol implementation to it makes the one crate
that cannot be unit-tested the crate holding the most new logic.

### The seam is a `Session` trait implemented by the composition root

`clayspace-mcp` defines a narrow trait and calls it on the interface thread:

```rust
pub trait Session {
    fn apply(&mut self, command: Command) -> Result<Applied, Refusal>;
    fn read(&mut self, query: StateQuery) -> StateReport;
    fn capture(&mut self, request: CaptureRequest) -> Result<Frame, Refusal>;
    fn settle(&mut self, budget: Duration) -> Settled;
    fn measure(&mut self, command: Command) -> Result<Measured, Refusal>;
    fn consent(&mut self, ask: &Consent) -> ConsentOutcome;
    fn gesture_in_progress(&self) -> bool;
}
```

Everything above it — HTTP, JSON-RPC, the catalogue, argument parsing, the
JSON→`Command` mapping, the gate table, the refusal vocabulary — is in
`clayspace-mcp` and is tested against a fake `Session`. Everything below it is
in `clayspace-app` and is ordinary composition-root work: apply a command, read
ViewModel fields into plain values, render offscreen, poll the job queue.

`Frame` crosses the seam as unencoded RGBA8 rows plus dimensions. PNG encoding
and base64 happen on the connection thread, off the interface thread, because a
1.5 MB encode inside a frame is a dropped frame for a result nobody is watching
in real time.

### The tool surface is a catalogue, and the compiler keeps it honest

Twenty-nine tools. Twenty-four are one per domain the application already has a
ViewModel or a panel for — `tool`, `brush`, `stroke`, `mask`, `curve`, `shape`,
`object`, `transform`, `lattice`, `subtool`, `boolean`, `layer`, `passes`,
`hierarchy`, `document`, `exchange`, `repair`, `convert`, `deform`, `armature`,
`history`, `view`, `reference`, `session` — each taking `{ action, arguments }`.
Five are not commands at all: `describe`, `state`, `viewport`, `wait`,
`measure`.

There is no camera group: the camera is moved by the pointer and has no
`Command` behind it, so what an agent gets is the four view presets and
`frame_all`. Free camera control would be new commands, and inventing them
here would be inventing a second way to move a camera.

The anti-drift mechanism is a single function in `clayspace-mcp`:

```rust
fn home_of(command: &Command) -> Home  // exhaustive match, no wildcard arm
```

A new `Command` variant fails to compile until it is given a group, an action
name and an argument shape. That is the whole reason the mapping is written by
hand rather than derived: a derive would silently accept a variant nobody
exposed. A variant deliberately not offered is named in an explicit
`Home::NotOffered(reason)` arm, so "why can't I call this" has an answer in the
source. Eight are: the five that open a native file panel on the sculptor's own
screen, and the three that open, shut or answer the agent door — an agent that
could answer the permission it is being asked for would have made the gate a
formality.

`describe` answers from the catalogue, and a test closes the loop in both
directions: every catalogue row builds a command from its own published
example, and `home_of` puts that command back on the row that built it. With
the match exhaustive, a variant with no home does not compile and a home with
no working row fails the test.

*Alternative considered:* one tool per `Command` variant. Rejected on the
proposal's grounds — a hundred and thirty tools is a list an agent chooses
badly from, and every new variant would become a protocol change.

### The armature's rigging gestures become commands

`home_of` is exhaustive over `Command`, which makes it a complete guard over
everything the command path already carries — and no guard at all over what it
does not. The armature was the case: growing a ZSphere is "drag a child out of
a parent" and lived on `ArmatureViewModel` as `press` / `drag` / `release`,
called straight from the pointer. Those were never `Command`s, so nothing
refused to compile and nothing appeared in `NotOffered`; the surface was
simply missing a limb and said so nowhere.

Six commands close it — `SelectZsphere`, `AddZsphere`, `InsertZsphere`,
`MoveZsphere`, `ResizeZsphere`, `ReparentZsphere` — and each says in one value
what the pointer says in three events. A press that names the parent, a first
movement that creates the child and a release are three only because a hand
cannot say "here" and "there" at once; `AddZsphere` says both. `MoveZsphere`
takes a **point rather than a displacement**, and is exact where a drag only
ends up close: the delta is worked out from the tree once instead of
accumulating over a gesture.

The tests hold the two paths against each other — a sphere grown by dragging
and a sphere grown by asking must be the same sphere, in the same place, with
the same selection after it.

What this does not do is make the guard complete. The lesson is the general
one: a verb that never entered the command path is invisible to a mechanism
built over that path, and finding the next one takes a person reading the
ViewModels rather than a compiler.

*Alternative considered:* deriving the argument schemas via `serde` on
`Command`. Rejected: it puts `serde` into `clayspace-vm`, which today depends
on `clayspace-model` and nothing else, and it exports the internal shape of a
type we refactor freely as a public wire contract.

### Requests are jobs the interface thread drains, and they wake it

A listener thread accepts; a thread per connection parses. A parsed request
becomes a job — the parsed work plus a `mpsc::Sender` for its reply — pushed
onto a `Mutex<VecDeque<Job>>` shared with the app. The connection thread then
blocks on its receiver with a deadline.

Waking is the reason `EventLoop::with_user_event` replaces `EventLoop::new`:
pushing a job is followed by `EventLoopProxy::send_event`, and `user_event`
drains the queue. `about_to_wait` drains it too, so a job that raced the wake-up
is not left until the next input.

The interface thread executes jobs in arrival order, and at most a bounded
number per frame — a burst from an agent delays itself rather than starving the
redraw. Ordering across clients falls out of the single queue, which is what
"two clients do not interleave" needs.

Two properties come free and are worth stating because they are load-bearing.
A changing tool returns only after `apply` has run, because the reply is sent
from inside the drain. And an agent request that stalls a frame appears in the
existing `FrameLog` under its own operation name, so the door's cost shows up
in the same place every other stall does.

*Alternative considered:* letting the server thread hold the ViewModels behind
a mutex. Not available — `Observable` is `!Sync` and the engine wrapper is
`!Sync`, so this is a borrow-check error rather than a design choice.

### The transport is a hand-written HTTP/1.1 subset

MCP Streamable HTTP on `127.0.0.1`: `POST /mcp` carrying one JSON-RPC message
and answering `application/json`, `GET /mcp` holding a `text/event-stream` for
server-initiated notifications, `DELETE /mcp` ending a session. Keep-alive,
`Content-Length` and chunked request bodies; nothing else. No CORS headers are
ever emitted, `Origin` is validated, and a request that is not on loopback
cannot arrive because nothing else is bound.

This is a few hundred lines with a table of conformance cases against it. The
protocol version this build implements is a named constant reported in
`initialize`, so an incompatibility is a negotiation failure rather than a
misparse.

*Alternative considered:* `rmcp` with `tokio`. It is the right answer in most
codebases and the wrong one here: the workspace has no async at all, the tree
would gain `tokio`, `hyper`, `tower` and their subtrees, and `deny.toml` and
the generated `ATTRIBUTION.md` are written on the understanding that a
dependency is something we audit and ship. The transport we need is a fraction
of what the SDK covers, and the fraction is stable.

*Alternative considered:* a Unix socket with a stdio bridge binary. Smaller,
but every client then needs the shim installed and pointed at the right
session, which is the friction this change exists to remove.

### Where the door is published, and what it costs

`SessionStore` gains `agente.acesso`, written `0600` at start and removed at
exit, carrying the port and a secret generated fresh each run. A client reads
one file to learn both. This follows the session directory's existing
convention — `sessão.aberta`, `recentes.txt`, `referências.txt` — rather than
inventing a second place for per-session state.

The secret is compared in constant time, and it never appears in the
diagnostics report, which is pasted into issues.

The blast radius is stated plainly: **any process running as this user can read
that file and drive the session.** That is the same boundary that already
protects the autosave and the recovery marker, and the reason destructive verbs
need a consent the file cannot supply.

### What is gated, and how consent is asked

Gated: save-over, save-as to an existing path, export, import that replaces,
open, new-over-unsaved, delete of a layer or subtool beyond undo's reach, and
quit. Ungated: everything recoverable through the edit history.

The gate table is keyed on `Command` in `clayspace-mcp` and is derived from
neither `touches_document()` nor `label()` — those answer different questions,
and a gate that drifts from its intent because it was inferred is worse than
one written down.

Consent comes from one of two places. An opt-in recorded in the session store
(`agente.consentimentos`, one kind per line), or an answer at the window. The
ask is state on a new `AgentViewModel` in `clayspace-vm`; the shell draws it
from that state and emits the answer as a command, so the View stays a pure
function of ViewModel state and the consent flow is testable headlessly. An ask
that is not answered within its bound is refused, which is what keeps a
connection from hanging on an unattended machine.

### Capture renders an extra frame rather than copying the presented one

A surface texture is not reliably `COPY_SRC` across backends, so reading back
what was just presented is not portable. `capture` renders one more frame into
an `OffscreenTarget` at the requested size, through the same `Renderer`,
`Camera`, shading, overlays and quality settings the window is using. The cost
is one frame's render per capture, paid only when asked.

**The target is in the window's format, not the offscreen default.** The
renderer's pipelines carry the surface's format — `Bgra8UnormSrgb` on macOS —
and a render pass whose colour attachment is a different format fails
validation, leaves the texture untouched, and returns a frame of transparent
black with the reason only in a log. The alternative, a second renderer built
for the offscreen format, is a second set of pipelines to keep in step with the
first, which is the drift this whole design is arranged to avoid. So the format
follows the window and the rows are put into RGBA order at the seam, where the
contract says they are RGBA.

The whole-window variant runs the `egui` pass into the same target after the
scene pass, which is how the panels reach the image. The viewport-only variant
is the default because it is the cheaper one and the one most answers need.

**Correlating the capture with the state.** A capture requested alongside a
command is taken after that command's dirty region has been re-meshed —
`settle_geometry_now` already exists for exactly this. Where a job or
maintenance is still outstanding, the answer carries what is outstanding
beside the image rather than pretending the frame is settled.

**The render floor** is measured on demand through the same path the two
captures went through, and reported with any difference, so an agent does not
read a macOS rasteriser's 1,294 differing pixels as a change. This is the rule
`visual-verification` already states, made available to a caller that is not a
test.

### Measurement says where it came from

`measure` runs one command with the clock around it on the interface thread and
returns wall time, whether a frame was stalled, the active backend, the
platform, and a marker saying this is a live-session figure. `state` exposes
the `FrameLog`, the memory ledger by part, and the fallback list — all values
the diagnostics report already assembles.

Nothing here writes `benchmarks/*.json`. A baseline moves the number every
future run is judged against, and a figure taken with a window open, panels
drawn and a person's session in memory is not that number.

## Risks / Trade-offs

**A hand-written transport drifts from the MCP specification** → the surface is
a few hundred lines, the implemented protocol version is a named constant
reported in `initialize`, and conformance cases live beside it. If the spec
moves in a way that costs more than it saves, the `Session` seam means only the
transport module is replaced — swapping in `rmcp` later touches nothing above
it.

**A person's gesture and an agent's are both "a gesture in progress"** → the
mid-gesture guard has to mean *a person is holding the pointer*, or an agent is
refused its own `stroke.continue` the moment it has opened a stroke. The
composition root records whose gesture is open; a person cannot open a second
while the engine holds one, so the two cannot be confused in practice.

**A hundred and thirty mapping arms are a hundred and thirty chances to get an
argument wrong** →
the exhaustive match makes omission impossible and a wrong shape visible; every
group's actions get a round-trip test; and the arms are mechanical enough to
review in one pass per group.

**An agent and a person editing at once** → a changing tool is refused during a
gesture, both share one history so an undo means the same thing to both, and
the status area attributes the last agent action. What remains — an agent
acting between a person's strokes — is the intended behaviour, not a race.

**A local process reads the secret and drives the session** → stated above;
loopback binding, `0600`, a secret per run, `Origin` validation, gating on
destructive verbs, and the interface's own control to stop the door.

**The door costs frames** → jobs are bounded per frame, encoding is off the
interface thread, capture is only on request, and a stall the server causes is
reported in the same log every other stall is, so a regression here is visible
rather than felt.

**`serde` in the tree** → confined to one crate by the layering check, at the
tool boundary only, and no domain or ViewModel type is given a derive that
would turn its internal shape into a wire contract.

**A whole application's capability behind one authentication** → the
first cut authenticates a client, not an *agent's task*. Per-tool
authorisation, if it is ever wanted, sits on the same gate table.

## Migration Plan

No data migration: nothing about a document, its format or the session store's
existing files changes. The crate is additive and the application runs without
it.

Four stages, each shippable:

1. **The door.** Crate, transport, `initialize`, `describe`, the `Session` seam
   against a fake, and the read-only tools — `state`, `jobs`, `session`. The
   window says it is listening. Nothing can change the document yet, which
   makes the whole transport reviewable at a blast radius of zero.
2. **Seeing.** `viewport` capture, viewport and whole window, the settle
   barrier, the render floor and comparison.
3. **Driving.** The command groups, the exhaustive mapping, mid-gesture
   refusal, and the ordering guarantees.
4. **Consent and measurement.** The gate table, the ask at the window, the
   recorded opt-ins, `measure`, and the diagnostics section.

**Rollback** is the menu toggle and the remembered choice: a build that ships
this can be run with the door shut, and a session with the door shut behaves
exactly as one from before this change. If the crate itself has to come out,
nothing above it depends on it — the composition root's wiring and the
`AgentViewModel` are the only removals.
